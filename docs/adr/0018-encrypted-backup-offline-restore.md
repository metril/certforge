# 0018: Encrypted backup archive format and offline, verified restore

Status: accepted (Phase 6A)

## Context

CertForge holds material that cannot be reissued or recovered by any other means: private keys under `crypto.root`, the ACME account keys and DNS credentials issuance depends on, and the append-only audit chain. A backup therefore has to satisfy two goals that pull in opposite directions. It must be safe to store anywhere — off-host, unencrypted storage, a third-party bucket — which means every secret it carries must stay encrypted at rest exactly as strongly as it is in the live database, under a key CertForge alone controls. And it must actually be restorable, offline, without a running server or a network call, onto a database that may be older, newer, or simply different from the one it came from, without silently loading something subtly wrong.

Two shapes were considered for the archive's encryption: use `pg_dump`'s own custom format plus a general-purpose encryption tool (age, gpg) as a wrapping step, or write a small, pure-Go format that does both at once. `pg_dump` needs the `pg_dump` binary available wherever a backup is taken or restored (contradicting the "pure Go, in-process" shape the rest of CertForge follows — `go-acme/lego` in-process, no shelling out, ADR 0001) and ties the key CertForge's own root secret to a second, external tool's own key handling. A hand-rolled format, built directly on `internal/crypto`'s existing envelope primitives and a plain `COPY ... TO STDOUT`/`COPY ... FROM STDIN` dump, needs nothing beyond the `database/sql` driver already in the binary, and lets the backup's own key derivation, KEK-mismatch detection and tamper detection all be first-class, tested Go code instead of shell-script glue around a separate tool's exit codes.

Restoring into a database whose schema does not already exactly match the backup's origin is unavoidable: 6A's own migration 00013 changed every foreign key to `DEFERRABLE`, precisely so a later restore (this task) can load tables out of dependency order — meaning a restore's very first job is deciding which schema version to load into, before a single row moves.

## Decision

- **The archive is a hand-rolled, chunked, authenticated stream — not an encrypted `pg_dump` file.** `Magic`, a length-prefixed plaintext JSON header, then AES-256-GCM chunks of at most `ChunkSize` (64 KiB) plaintext each, length-prefixed. The plaintext underneath is a `tar` of one CSV file per table (Postgres's own `COPY ... (FORMAT csv, HEADER)` output, unmodified) plus a final `manifest.json` entry. Nothing about the format depends on a `pg_dump`/`pg_restore` binary being present, matching the rest of CertForge's in-process design.
- **The header is plaintext, and every chunk is bound to its exact bytes.** Identifying a backup — its creation time, its migration version, which KEK it needs — must not itself require a key; `ReadHeader` needs none. But the header also carries `RootSealed`, the sealed `crypto.root` row, which restore trusts completely before writing anything, so it cannot be allowed to drift from what was actually used to derive the stream key. Each chunk's GCM additional data is `sha256(magic‖header)‖index‖final`, so a single flipped header byte fails every chunk's authentication the moment it is opened, not just a header-level checksum a tool could choose to skip.
- **The stream key comes from the root secret, not the KEK directly, and never repeats.** `DeriveKey(DeriveKey(root, "certforge-backup"), hex(salt))`, with a fresh random 16-byte salt per archive. Deriving from `root` (rather than straight from the KEK's bytes) keeps this consistent with every other derived key in the system (ADR 0014) and, in particular, survives a KEK rotation: an in-progress rewrap does not change which stream key a backup taken mid-rotation would use, since `root` itself is untouched by rewrap. The archive-unique salt means two backups of an unchanged database never produce identical ciphertext, which would otherwise leak that nothing had changed between them.
- **A chunk's finality is structural, not a stored flag the reader is asked to trust.** The AAD's last byte says whether a chunk is the final one, but the *reader* decides that by looking one chunk ahead in the stream (`chunkReader`'s lookahead), not by reading a flag out of the (attacker-controlled) bytes themselves. A dropped final chunk leaves the stream's last present chunk still carrying its original, non-final AAD; the reader — finding nothing after it — assumes finality and gets authentication failure instead of a truncated-but-accepted restore. Chunk reordering and trailing garbage fail the same way, for the same reason: the AAD the reader computes depends on structural position, not on anything the bytes themselves claim to be. A length prefix is also bounded (`maxChunkCiphertext`) before it is ever used to allocate, so a handful of hostile bytes cannot themselves force a multi-gigabyte allocation.
- **Row counts and content hashes live in an encrypted `manifest.json` tar entry, not the plaintext header.** The header is written before the dump starts (Write's own `REPEATABLE READ` snapshot needs to record its migration version before touching any table), so it cannot yet know any table's row count or hash. Deferring those to a final, encrypted entry also means a header inspection alone (`ReadHeader`, no key) reveals table *names* but nothing about their size or content — useful for a CLI's pre-restore summary without also being a content oracle.
- **Restore is one transaction, deferred constraints, verify-then-commit.** `SET CONSTRAINTS ALL DEFERRED` lets tables load in the archive's own order regardless of foreign-key direction (migration 00013 made every non-river foreign key `DEFERRABLE INITIALLY IMMEDIATE` for exactly this). Every table's loaded row count and content hash are checked against `manifest.json` while still inside the transaction; so are two final checks that have nothing to do with the manifest at all — the restored `crypto.root` row must equal the header's `RootSealed` byte for byte, and the caller's canary must still open — before `Commit` is ever called. Any failure at any point rolls the whole transaction back: a wrong KEK, a truncated file, a crafted archive with a swapped `crypto.root`, or a canary that will not open under the configured envelope all leave the target database exactly as it was, never partially loaded.
- **The migration target is `max(header.MigrationVersion, 13)`, decided before any row loads.** `MigrateTo` (new in `internal/db`) runs goose up to exactly that version and then river's own schema (`migrateRiver`), the same two steps `Migrate` always runs, so a restored database is never left with an application schema but no river tables. A target database already migrated *past* that version (`db.Version` reads higher) refuses outright (`ErrNewerDatabase`): there is no down-migration path, and loading old rows against unknown newer schema would be a guess, not a restore.
- **`audit_events` is loaded, never truncated, by design.** Its own append-only triggers (`00001_init.sql`, added long before this task) refuse `TRUNCATE`, `UPDATE` and `DELETE` unconditionally except for the narrow HMAC-rechain case (ADR 0008) — and restore does not attempt to work around that by any privileged path (no `ALTER TABLE ... DISABLE TRIGGER`; the application's own database role is not assumed to own its tables, matching ADR 0008's original reasoning for not disabling the trigger there either). Its rows are still copied in via plain `COPY ... FROM STDIN` (an insert, never blocked by those triggers), landing on top of whatever the target database's audit chain already held. A restore can add history; it can never erase it, even its own operator's.
- **Every non-generated column is dumped and restored by name, not by position.** `Write` queries `information_schema.columns` per table (excluding any `is_generated = 'ALWAYS'` column — Postgres refuses those in a `COPY FROM` column list) to build the `SELECT` list for `COPY ... TO STDOUT`; `Restore` reads each CSV entry's own header row to build the matching `COPY ... FROM STDIN` column list, rather than trusting the live schema's current column order to still match. Sequence-backed columns (`bigserial`, found via `column_default LIKE 'nextval(%'`) are reset to one past their loaded maximum after loading, since `COPY FROM` writes explicit primary keys without advancing the sequence that normally supplies them.

## Consequences

- A lost KEK makes every backup taken under it permanently unrestorable. This is the same tradeoff CertForge already makes for the live database (`docs/security.md#kek-handling`: "escrow the KEK outside the server; without it, backups cannot be decrypted") — this task is what makes that sentence literally true, rather than aspirational. `createBackup` (Task 12) will refuse to run until an operator has explicitly confirmed KEK escrow.
- `backup.Manifest` is a fixed, hand-maintained table list (`internal/db` package comment on why: it is the load order, `goose_db_version` first, no `river_*`), checked against `information_schema` by a standing test (`TestManifestCoversAllTables`) rather than derived automatically. A future migration that adds a table and forgets to add it here would silently never be backed up — the standing test exists specifically to make that impossible to miss.
- `internal/backup` is a library only in this task: `Write`, `Restore`, and their supporting types, with no CLI, no HTTP endpoint, and no serve-time lock yet. Task 11 adds the `certforge backup`/`restore` commands and the advisory-lock pair (`AcquireServeLock` for a running server, an exclusive lock for restore) that keeps a live server and a restore from ever running against the same database at once. Task 12 adds the streaming API endpoint, the schedule, and `/readyz`'s `checks.backup`.
- Every backup dump runs inside one `REPEATABLE READ, READ ONLY` transaction, so a large database's dump duration is a long-held snapshot, not a long-held lock — no other transaction is blocked by it, but Postgres must keep enough MVCC history alive for its duration. This is the same tradeoff `pg_dump` itself makes for consistent dumps and is not new to this format.
