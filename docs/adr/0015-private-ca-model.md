# 0015: Private CA model — root plus issuing intermediate, per-issuer CRL, retired keys kept until expiry, no OCSP

Status: accepted (Phase 5A)

## Context
Phase 5A adds `localca`, CertForge's own private certificate authority, alongside `acme` (external directories). Task 6 built the pure certificate logic (`internal/signer/localca`: `Generate`, `Import`, `Rotate`, leaf `Issue`, `BuildCRL`) with no I/O of its own. This task (5A Task 7) wires it to the CA lifecycle API, persistence and revocation, and needed answers to four questions Task 6 deliberately left open: how a CA's issuing key gets rotated without invalidating certificates it already issued, how revocation reaches a CRL at all (nothing called `Signer.Revoke` before this task), how a rotated-away issuing key stays available long enough to revoke against, and whether to build OCSP alongside CRL.

## Decision
- **Two certificates, not one.** A generated `localca` CA is a self-signed root (`KeyUsageCertSign | KeyUsageCRLSign`, path length 1) whose private key is sealed and touched only by `Rotate`, plus an issuing intermediate the root signs, whose private key does the actual day-to-day work (`Issue`, `Revoke`, `BuildCRL`). A single root key never signs leaves or CRLs directly, so rotating the issuing key never requires re-trusting anything: every leaf already deployed still chains to the same root, unchanged.
- **Rotate retires, never deletes.** `POST /orgs/{orgId}/cas/{id}/rotate` signs a fresh issuing intermediate under the held root and moves the current one into `config.retired[]` (its certificate, kept public — a leaf's issuer is public information) with its sealed key kept alongside in `secret_cfg.retired[]`, matched by serial. Deleting a rotated-away key immediately would make every leaf it signed permanently unrevocable and its CRL forever frozen at whatever it last said — a live intermediate is worse than a slightly larger secret blob. A retired key is purged only once its own certificate's `notAfter` has passed (checked at the next rotate), since nothing it signed can still be presented as valid past that point anyway.
- **Every issuer gets its own CRL; revocation picks the issuer that actually signed the leaf.** `GET /crl/{caId}.crl` is the current issuer's; `GET /crl/{caId}/{issuerSerial}.crl` serves any issuer the CA has held. A CRL's signature must verify against its own issuing certificate (RFC 5280), so a single merged CRL across every issuer a CA has ever had was never an option once revoking a leaf from a retired issuer had to work. `RevokeVersion` determines the right issuer by the leaf's `AuthorityKeyId` (matching the current issuer's `SubjectKeyId`, or a retired one's) before building a `Signer` over that specific issuer's material — never the leaf's issuer name or a caller-supplied hint, both of which a client could get wrong or omit.
- **One `crl_number` counter per CA, not per issuer.** RFC 5280 only requires a CRL's number to be non-decreasing across CRLs from the *same* issuer; a single counter bumped on every revocation regardless of which issuer signed the revoked leaf satisfies that trivially (each issuer's own sequence is a non-decreasing subsequence of the shared counter) while keeping the persisted state to one integer instead of one per issuer, including retired ones.
- **No OCSP.** A CRL is a single flat, cacheable, unauthenticated GET with no per-request server load beyond a cache lookup; OCSP needs a live responder, a separate signing identity (or delegation), and per-request signing — real operational cost for a self-hosted private CA whose whole audience is the operator's own fleet, which already polls a CRL far more cheaply than it could poll OCSP for every TLS handshake. Nothing in the leaf template sets an Authority Information Access OCSP URL, so clients that check are not misdirected to a service that does not exist.
- **`secret_cfg` and `config` are the only two places key material and its public shadow live** — no separate table, no per-key row. A sealed JSON blob (`{rootKey?, issuingKey, retired[], importKeyPem?}`) mirrors the public `config` JSON almost field-for-field (`issuingPem`/`retired[].pem` vs. `secret_cfg.issuingKey`/`secret_cfg.retired[].key`, matched by serial), so the CA's whole current and historical state reads as one coherent pair of documents instead of being scattered.

## Consequences
- Revoking a leaf from a retired issuer works exactly like revoking one from the current issuer, from the caller's point of view — the API takes no `issuerSerial` parameter at all; the server works it out. A leaf whose issuer has both rotated away *and* expired can no longer be revoked (there is nothing to revoke against — its own certificate is already unusable), which is the same terminal state an expired certificate reaches on any CA.
- An imported CA (no held root key) can never rotate — `RotateCA` is 422 for it — since there is no key to sign a new issuing certificate with. It can still revoke and serve a CRL for its single issuer for as long as that issuer's own certificate remains valid.
- `internal/issuance.SignerFactory` (new this task, localca only; Task 9 adds `acme`/`vaultpki` and removes `worker.DefaultSigner`) always builds a signer over a CA's *current* issuer — retired-issuer revocation goes through a separate, lower-level path (`Store`'s own material construction) that only the locked, transactional revoke flow uses, since only it ever needs to touch a specific retired issuer's key.
- A future signer kind that also needs "revoke against a rotated-away key" (`vaultpki`, Task 8) will either reuse this same retired-key-until-expiry shape or explicitly document why Vault's own PKI secrets engine handles it differently (Vault PKI has its own CRL and revocation list built in, so it likely needs none of this).
