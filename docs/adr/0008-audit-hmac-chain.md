# 0008: Keyed audit hash chain

Status: accepted (Phase 2)

## Context
Phase 1 linked audit rows with plain SHA-256. Anyone with write access to the table could rewrite the whole tail consistently.

## Decision
- Each row's hash is HMAC-SHA256 over (`hash_alg` label, prev_hash, ts, actor, action, resource, org, ip, canonical details), keyed with `HKDF-SHA256(KEK, info "certforge-audit")`. `hash_alg` records the algorithm per row (`sha256` or `hmac-sha256`). Folding the algorithm label itself into the MAC input (fix round 1, item 3) means `hash_alg` cannot be swapped on a row without invalidating its hash — the hash commits to which algorithm produced it. Legacy `sha256` rows keep their original, unprefixed formula unchanged, so `Rechain` can still verify rows written before this field existed.
- At startup, after the KEK canary passes, `audit.Rechain` converts legacy rows once, inside one transaction under the append advisory lock. It first verifies every row with its stored algorithm and refuses (no change, error logged) if the legacy chain is already broken.
- `Rechain` does not disable the append-only trigger: table ownership (needed for `ALTER TABLE ... DISABLE TRIGGER`) conflicts with the planned non-owner application role. Instead, migration 00006 rewrites the trigger function itself to allow an `UPDATE` that changes only `hash`, `prev_hash` and `hash_alg`, landing only on `hash_alg = 'hmac-sha256'` (never back to `sha256`), and leaves every other column (and `id`) unchanged; any other `UPDATE`, and every `DELETE`/`TRUNCATE`, is still rejected exactly as before. `Rechain`'s own `UpdateAuditChain` query only ever touches those three columns and only ever sets `hmac-sha256`, so it needs no special privilege beyond ordinary `UPDATE` on them. **The trigger is a defense-in-depth backstop, not a proof of integrity on its own**: an `UPDATE` that keeps `hash_alg = 'hmac-sha256'` while writing a wrong `hash` is still allowed by the trigger (it cannot check the MAC) — only `Check`, verifying with the real key, catches that.
- **The downgrade gate is two independent checks, either of which is enough to reject a `sha256` row.** (1) A monotonic rule over the rows themselves (fix round 1): both `Check` and `Rechain` walk the chain in id order and track whether a `hmac-sha256` row has been seen; once one has, any later `sha256` row is reported/refused as broken outright, even if that row is internally consistent under its own stored (unkeyed) algorithm — an attacker without the KEK can still forge a valid legacy-formula hash, so a row's own consistency proves nothing once a keyed row has appeared. `Rechain` applies this gate *during* its verification pass, before rewriting anything, so a forged legacy row appended after re-keying is refused rather than laundered into a freshly-rewritten, valid HMAC row on the next re-chain. (2) The `audit.chain_keyed = true` flag in the `settings` table, written by `Rechain` once no legacy row remains, in the same transaction as the re-chain commit — read back up front by both `Check` and `Rechain` (fix round 2): once set, ANY `sha256` row is rejected, even if the monotonic rule alone would never trip on it. This closes the gap the monotonic rule leaves open on its own: an adversary with table-owner access can bypass the trigger and replace the *entire* table with a self-consistent, legacy-only `sha256` chain, in which case no `hmac-sha256` row is ever reachable to trigger rule (1) — rule (2) still catches it, and `Rechain` refuses to rewrite such a chain rather than treating it as ordinary unconverted history. This is a mitigation, not a full fix: an adversary who can replace the table's contents can, in principle, also delete or reset the `audit.chain_keyed` setting row itself (an ordinary row in the same database, under the same owner access), which would defeat gate (2) too — closing that residual needs external head-hash anchoring (still an open known gap, below).
- `bootstrap-admin` runs the KEK canary (`Store.EnsureCanary`) before constructing its `Auditor`, and refuses outright on a wrong KEK, so it never writes rows keyed wrong.
- `serve` cannot refuse outright the same way (fix round 3): it must keep serving so `/readyz` keeps reporting the failure. Instead, on a failed canary it constructs its `Auditor` with `audit.NewDisabled` rather than `audit.New`: `Record` then always returns `ErrAuditUnavailable` without touching the database. Most handlers log that error and continue (the write is best-effort); a handler whose audit trail is load-bearing — certificate key/material download, `bootstrap-admin`'s own separate canary check — fails closed instead, propagating the error rather than serving without a corresponding row. `Rechain` refuses too on a disabled `Auditor` (belt and braces: `serve` already skips the call outright via its own `canaryOK` gate, but `Rechain` doesn't rely solely on that). `Check`/`Verify` still run against the derived key as before — best-effort diagnostics over whatever is already in the table, unaffected by the disabled state; `GET /audit/verify` is not gated by any of this. This closes the gap where `serve` previously built a recording `Auditor` from an untrusted derived key even when the canary had already failed, silently writing rows that `Rechain` could never later verify.
- `GET /audit/verify` walks the chain (cached 60 s) and reports the first bad row.

## Consequences
Appending or altering rows needs the KEK: a forged or relabelled row's hash still has to verify under it, and both downgrade gates reject a legacy-formula row once the chain is known to be keyed. An attacker with table-owner access who also deletes or resets the `audit.chain_keyed` setting row can still replace history wholesale with a self-consistent legacy-only chain that passes `Check` clean — only external head-hash anchoring (still an open known gap, below) closes that residual; owner access to the database was always going to be a strong position, and this ADR does not claim to fully defend against it. Starting the server with the wrong KEK skips re-chaining (readiness already fails in that state), but any event still recorded while running under the wrong KEK is keyed wrong and fails verification under the right one. KEK rotation (Phase 5) must re-derive the audit key and re-chain, or carry the old derived audit key forward. Still open: anchoring the head hash outside the table, and running the application under a role that does not own `audit_events`.
