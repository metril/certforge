# 0016: Client-less grants — a parallel dispatcher, not a fake agent

Status: accepted (Phase 5A)

## Context

Phase 5A Task 10 added `vault-kv`, the first deploy target type that runs on the server rather than on an enrolled agent (`internal/deploy.RunsOn`). A grant onto it has no client at all: `client_cert_grants.client_id` is nullable (migration 00012), and the whole `agents` package — rendering, revisions, the WebSocket hub, drift, hooks — exists to reconcile a *client's* state with what the server wants, none of which applies when there is no agent to reconcile. Task 11 had to decide how such a grant actually gets deployed and its status reported, given the deviation R9/R6 already settled that it is a separate API shape (`createServerGrant`/`listTargetGrants`, `Grant.runsOn`/`serverDeployment`), not a client grant with a null client shoehorned through the agent path.

## Decision

- **A second, parallel `issuance.VersionListener`, not a synthetic agent.** `internal/deploy.Dispatcher` hears about every new certificate version exactly like `agents.Service` does, but independently: it never touches `client_cert_grants` rows that have a client, and `agents.Service` never touches ones that don't (every `LiveGrantIDs*`/`StaleDeploymentGrantIDs` query the agent side runs filters `client_id IS NOT NULL`). The two listeners are registered side by side in `cmd/certforge/serve.go`, both before `riverClient.Start`. This means no shared code path can accidentally leak a server grant into `agents.render`'s client-locking, path-collision or push-nudge logic — none of which makes sense for something with no client — at the cost of a genuinely separate (if structurally similar) render step in `Dispatcher.deploy`'s own `renderFiles`.
- **`server_deployments`, not `deployments`.** A client grant's `deployments` row exists because an agent *reports* what it installed (`installed`, `reported_at`) separately from what the server *expects* (`expected`) — drift is the gap between the two. A server grant has no such gap: `Dispatcher` both renders and writes the material in the same job, so there is nothing to report back. `server_deployments` is deliberately smaller — `status` (`pending`/`deployed`/`failed`), the version deployed or being deployed, `last_error`, `deployed_at` — with no `expected`/`installed` digest pair and no drift concept at all.
- **One river job, not a bundle-and-relay dance.** A client grant's deploy goes through `agentproto.Bundle`/hooks/the hub because it has to cross a network boundary to a process the server doesn't control. A server grant's "agent" is the server's own `deploy.Target.Deploy`, called in-process by a river worker (`certforge_server_deploy{grantId, versionId}`, unique per grant while not completed, 5 retries with backoff) — the same job-queue machinery every other background attempt in this codebase already uses (`certforge_issue`, `certforge_kek_rewrap`), rather than a bespoke direct-call-on-commit that river's retry/backoff/observability would otherwise have to be reinvented for.
- **Redaction is the `Target`'s job, truncation is the `Dispatcher`'s.** `Dispatcher.fail` bounds `last_error` to 1000 characters and nothing else; it never calls `vault.Client.Redact` itself; because it doesn't hold a `*vault.Client`, and because a future `Target` type talking to a different secret store would need its own redaction anyway. Every `internal/vault.Client` method already runs its return error through `Redact` (ADR-adjacent to the Vault client's own contract, R10), so any error a `vault-kv` deploy attempt produces is safe to store verbatim by the time `Dispatcher` sees it. A `Target` implementation that talks to a secret it must redact is responsible for doing so before returning.
- **No soft-delete.** A client grant's delete waits on the agent to confirm its files are gone (`removed_at`, `removed_revision`) because the server cannot make the agent's filesystem match its own view synchronously. A server grant's deploy is the server's own synchronous (well, one-hop-via-river) action, so `deleteServerGrant` always hard-deletes at once; `server_deployments` follows via `ON DELETE CASCADE`. There is nothing analogous to "an agent might still be running with stale files" to wait for.

## Consequences

- Server grants are invisible to every piece of agent-facing UI, drift detection and the hourly agent sweep, by construction rather than by a special case sprinkled through `agents`; a future server-run target type gets this for free.
- A server grant's own status page has no "connected"/"online" concept (that's a property of an agent's socket, not of a river job) — `serverDeployment` is deliberately a smaller shape than `deployment`, and 5B's UI must not try to reuse the agent-grant status component unmodified.
- A `Target` implementation that returns an unredacted secret in an error leaks it into `last_error` (and thus, eventually, an API response) — this is a contract on `Target.Deploy`, not something `Dispatcher` can enforce mechanically. `vault-kv` upholds it because every `vault.Client` method already does; a future `Target` type must do the same.
- Retrying a failed server deploy is `redeployGrant` on the grant, exactly like a client grant — the API surface stays uniform even though the two kinds' backing mechanics (river job vs. WebSocket nudge) are unrelated.
