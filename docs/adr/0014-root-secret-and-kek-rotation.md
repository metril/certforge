# 0014: Root secret, multi-wrapper KEK rotation, no kek_id columns

Status: accepted (Phase 5A)

## Context
Before this phase, every derived key (the audit HMAC key, the OIDC state HMAC key) was `crypto.DeriveKey(kek.Key, ...)`, straight off the configured KEK's own bytes, and every `crypto.Envelope` held exactly one `KeyWrapper`. Rotating the KEK — swapping a static key for another, or moving to Vault Transit — had no defined path: it would silently change every derived key (forking the audit chain, Task 4's Review Focus T4) and leave every already-sealed row undecryptable the moment the old KEK stopped being configured. Task 4 broke the first half of that problem: `settings.RootKey` ("crypto.root") holds 32 bytes every derived key now comes from, seeded once and never touched by a KEK rotation itself. This task (5A Task 5) covers the second half: decrypting old data during and after a rotation, and moving it onto the new KEK without an offline migration step.

Three shapes were considered for tracking which KEK sealed a given row: (a) a `kek_id` column added to every table with a sealed column, (b) a side table mapping row → KEK id, (c) folding the id into the sealed value's own header. (a) and (b) both need a migration and a backfill for every existing sealed row, and a new column that must be kept in sync with the value on every write. (c) needs neither: `crypto.Blob.KEKID` (Task 4's format) already carries it as the blob's own plaintext prefix, readable without decrypting anything.

## Decision
- **No `kek_id` columns, ever.** The KEK id lives only in `crypto.Blob.KEKID`, alongside the wrapped DEK it names. `internal/kek.RewrapWorker`'s summary pass (`blobKEKID`) reads it by unmarshalling the stored bytes, never by decrypting — the same trick `settings.canaryKEKID` already used in Task 4 to match the canary's original KEK without needing to decrypt it first.
- **`crypto.Envelope` holds one active `KeyWrapper` plus zero or more previous ones.** `NewEnvelope(active, previous...)` panics on a duplicate id (an internal invariant a caller should never hit; `cmd/certforge/kek.go`'s `buildKEK` checks for it explicitly first and returns a clean boot error instead). `Encrypt` always uses the active wrapper; `Decrypt` picks whichever wrapper's id matches the blob's `KEKID`, so every previously-sealed row keeps decrypting for as long as its previous KEK is still configured (`CF_KEK_PREVIOUS[_FILE]`, `CF_KEK_PREVIOUS_VAULT_*`) — no maintenance window, no "decrypt everything under the old KEK before flipping over."
- **Rewrap decrypts and re-encrypts through the Envelope, never re-wraps the DEK in place, for a previous→active move.** `Envelope.Encrypt`'s AEAD binds the KEK id into the ciphertext's own additional data (`aead.Seal(..., []byte(id))`); relabelling `Blob.KEKID` onto the same ciphertext without a fresh `Encrypt` call would authenticate under the wrong id and fail every subsequent read. `RewrapWorker.rewrapBlob` therefore calls `Env.Decrypt` then `Env.Encrypt` for that case — a fresh DEK, nonce and ciphertext each time, exactly as if the row were written new. The one exception is a Transit key-version bump on the *active* KEK (`TransitWrapper.Rewrap`, called through the `crypto.Rewrapper` interface): the id does not change there, so only the wrapped DEK is replaced, and Vault's own rewrap operation never exposes the DEK to the application at all.
- **Every rewrap write is a compare-and-swap, never a blind overwrite.** `UPDATE ... SET col = $new WHERE pk = $pk AND col = $old`, where `$old` is the exact bytes `RewrapWorker` read and decrypted. Zero rows affected means something else wrote that column since the read — the new value is kept as-is (it was never decrypted, so overwriting it would either destroy live data or silently revert a legitimate concurrent write) and the row is counted in `remaining` for the next run to pick up.
- **The canary is rewrapped first, as an explicit, separate step.** `settings.CanaryKey` is one row inside the `settings` table `RewrapWorker` would reach anyway (first in `Tables`' visit order), but checking it before the main walk turns a fundamental problem — a previous KEK removed from `CF_KEK_PREVIOUS*` too soon, or genuinely wrong key bytes — into an immediate, cheap failure instead of one discovered only after scanning however many rows come before it alphabetically.
- **Progress is public, resumable state, not a private job detail.** `RewrapStatus` is written to `settings.RewrapKey` after every page (not just at the end), so `GET /keys/status` reflects an in-progress run, and a crashed or cancelled run resumes cleanly on the next attempt: already-active rows are cheap no-ops on a rescan, and the compare-and-swap makes a partial previous pass safe to repeat.

## Consequences
- A KEK rotation is: configure the new one as `CF_KEK`/`CF_KEK_VAULT_*` and the old one as `CF_KEK_PREVIOUS[_FILE]`/`CF_KEK_PREVIOUS_VAULT_*`, restart. Boot enqueues a rewrap automatically (`Service.EnqueueIfNeeded`) whenever there is a previous KEK configured or the active one can itself be rewrapped in place; `POST /keys/rewrap` (`startRewrap`) re-runs it on demand (409 while one is already queued or running). Once `GET /keys/status`'s `rewrap.remaining` reaches 0, the previous KEK's environment variables can be safely dropped.
- Every table with a sealed column needs its own keyset-paginated `SELECT ... WHERE pk > $after ORDER BY pk LIMIT $n` and its own single-column compare-and-swap `UPDATE`, in `internal/db/queries/rewrap.sql` — eight columns across seven tables (`cas` holds two, `eab_hmac` and `secret_cfg`, visited and reported together as one `RewrapTable`). A future sealed column (a new signer kind's imported key material, say) must add its own pair of queries here and a `tableColumns` entry, or it is silently invisible to rotation — nothing else enforces that a new `bytea` column sealing a `crypto.Blob` gets wired in.
- `internal/kek.Store` (the paging/CAS interface `RewrapWorker` runs against) is deliberately independent of Postgres specifics, which is what let `rewrap_test.go` cover the paging, counting and lost-race logic entirely in memory (`fakeStore`), with real `crypto.KeyWrapper`s doing the actual sealing — no database needed to prove the algorithm correct, only `rewrap_integration_test.go`'s `TestRewrapAllEightColumns` needs one, to prove the eight real columns are wired up right.
- A blob sealed under a KEK id that matches neither the active wrapper nor any configured previous one (an operator who dropped `CF_KEK_PREVIOUS*` before `remaining` reached 0, most likely) is undecryptable until that KEK is reconfigured — by design: there is no silent data loss path, only a loud one (`crypto.ErrWrongKEK`, surfaced as the rewrap job's `status.error` and, at read time, wherever that row is next accessed).
